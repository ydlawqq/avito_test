# Инструкция для модели: Candidate Generation для поиска услуг Avito

## 1. Контекст

Пользователи Avito ищут услуги короткими поисковыми запросами, например:

* «автоподбор»;
* «скупка телевизоров»;
* «баня на дровах»;
* «монтаж видеодомофонов»;
* «обзвон по базе».

Для каждого поискового запроса в корпусе может находиться большое количество объявлений исполнителей.

Поиск работает в несколько этапов:

1. **Candidate Generation** — быстро выбирает небольшое количество потенциально подходящих объявлений из всего корпуса.
2. **Ranking** — более сложные модели ранжируют только отобранных кандидатов.

В этой задаче необходимо реализовать именно первый этап — **кандидатогенерацию**.

Ключевое требование этого этапа — **полнота (recall)**.

Если релевантное объявление не попало в кандидаты на первом этапе, последующая модель ранжирования уже никогда не сможет его вернуть.

Поэтому задача не заключается в том, чтобы идеально расположить объявления по релевантности. Нужно обеспечить, чтобы **как можно больше релевантных объявлений оказалось среди первых 50 кандидатов**.

---

## 2. Задача

Необходимо построить алгоритм, который для каждого поискового запроса:

1. принимает признаки запроса;
2. ищет подходящие объявления в корпусе;
3. возвращает не более 50 `item_id`.

Для каждого запроса необходимо выбрать до 50 объявлений из корпуса.

Релевантными считаются объявления, которые пользователь действительно выбрал по этому поисковому запросу.

Обычно для одного запроса релевантным является одно или несколько объявлений.

Главная цель:

> Максимизировать **Recall@50** на benchmark-запросах.

Важно учитывать специфику задачи:

* порядок 50 объявлений не влияет на метрику;
* важно именно попадание релевантного объявления в множество из 50 кандидатов;
* reranking внутри top-50 не улучшает Recall@50;
* алгоритм должен работать на всём корпусе объявлений и быть воспроизводимым локально.

## 3. Данные

Доступны три Parquet-файла.

### 3.1. `train.parquet`

Обучающая выборка примерно из **497 673 строк**.

Каждая строка представляет пару:

> поисковый запрос → объявление, выбранное пользователем.

В строке находятся признаки как поискового запроса, так и объявления.

Пример:

```text
search_query = "автоподбор"
search_infm_params_text = "Рейтинг пользователя 4 звезды и выше"
item_title_raw = "Автоподбор Разовый осмотр автомобиля"
```

Такая строка означает, что пользователь выполнял поиск по запросу «автоподбор» с определёнными фильтрами и выбрал конкретное объявление.

### 3.2. `benchmark_queries.parquet`

Содержит **2 452 поисковых запроса без разметки**.

Для каждого запроса доступны:

* `query_id`;
* признаки запроса.

Колонки:

```text
query_id
search_query
search_location_id
search_is_delivery_search
search_infm_params_text
search_category
```

### 3.3. `benchmark_items.parquet`

Содержит корпус из **189 212 объявлений**.

Для каждого объявления доступны:

```text
item_id
item_title_raw
item_description_raw
item_infm_params_text
item_category_id
item_microcat_id
item_price
item_rating
item_rating_reviews_count
item_location_id
item_latitude
item_longitude
item_is_phone_hidden
item_is_message_forbidden
```

Все релевантные объявления для benchmark-запросов находятся внутри этого корпуса.

## 4. Признаки

### Признаки поискового запроса

#### `search_query`


Идентификатор локации, в которой выполнялся поиск.



Категория, в которой выполнялся поиск.

## 5. Формат решения

Алгоритм должен принимать:

```text
search query + признаки запроса
```

и искать подходящие объявления среди:

```text
benchmark_items.parquet
```

Результат для каждого запроса:

```text
до 50 item_id
```

Необходимо сформировать файл:

```text
answer.csv
```

с двумя колонками:

```text
query_id,answer
```

Пример:

```text
query_id,answer
00WuFMaXSFZBxSzT,1382564bf8994a83 121fa7f5e765ce00 f3801ec4fa472597
03ztb1gtRFC4K4vP,b0dd913d84ca1f61 e36f6c3245e05ab6 a3c3aa4703977bfe
```

### Требования к `answer.csv`

Файл должен:

* содержать ровно две колонки: `query_id` и `answer`;
* содержать одну строку для каждого `query_id` из `benchmark_queries.parquet`;
* не содержать пропусков;
* не содержать повторяющихся `query_id`;
* содержать не более 50 `item_id` для одного запроса;
* не содержать повторяющихся `item_id` внутри одного ответа;
* содержать только `item_id`, существующие в `benchmark_items.parquet`;
* использовать оригинальные значения `item_id`;
* не содержать дополнительного индекса.

Рекомендуемый способ сохранения:

```python
answer = pd.DataFrame({
    "query_id": query_ids,
    "answer": [" ".join(top50) for top50 in predictions],
})

answer.to_csv("answer.csv", index=False)
```

`query_id` и `item_id` должны сохраняться как строки.

## 6. Метрика

Основная метрика:

# Recall@50

Для одного запроса:

```text
Recall@50 =
    количество релевантных объявлений,
    попавших в top-50
    /
    общее количество релевантных объявлений
```

Формально:

```text
Recall@50 =
|Top50 ∩ Relevant|
------------------
     |Relevant|
```

Затем Recall усредняется по всем benchmark-запросам:

```text
mean(Recall@50(query))
```

Пример:

| Запрос | Релевантных | Попало в top-50 | Recall |
| ------ | ----------: | --------------: | -----: |
| A      |           1 |               1 |    1.0 |
| B      |           2 |               1 |    0.5 |
| C      |           1 |               0 |    0.0 |

Итог:

```text
(1.0 + 0.5 + 0.0) / 3 = 0.5
```

### Ключевое следствие

**Порядок объявлений внутри top-50 не имеет значения.**

Например:

```text
[A, B, C, D, E]
```

и

```text
[E, D, C, B, A]
```

имеют одинаковый Recall@50.

Поэтому задача отличается от обычного ranking:

* не нужно оптимизировать NDCG;
* не нужно оптимизировать MAP@50;
* не нужно максимально точно сортировать top-50;
* необходимо максимально увеличить вероятность того, что релевантное объявление вообще попадёт в эти 50.

Доступно **7 попыток**, засчитывается лучший результат.

Запрещено:

* хардкодить ответы для конкретных `query_id`;
* вручную восстанавливать тестовую разметку;
* копировать решения других участников;
* обращаться к внешним API во время работы решения.

Решение должно:

* воспроизводиться локально;
* работать без внешних API;
* быть применимо к произвольным benchmark-запросам;
* использовать только доступные данные и локальные модели/библиотеки.

Разрешено использовать:

* классические ML-модели;
* нейронные сети;
* методы Information Retrieval;

* TF-IDF;

* bi-encoders;
* cross-encoders;
* гибридные методы;

# Главное направление оптимизации

При разработке решения необходимо постоянно исходить из того, что целевая метрика — **Recall@50**.

Следовательно, retrieval должен быть ориентирован на **максимальную полноту**, а не на идеальное ранжирование.

Особенно полезно рассматривать задачу как retrieval pipeline:

```text
Query
  │
  ├── lexical retrieval
  │      └── BM25 / TF-IDF / exact match
  │
  ├── semantic retrieval
  │      └── embeddings / vector search
  │
  ├── structured filtering
  │      └── category / microcat / location / filters
  │
  └── дополнительные retrieval-сигналы
          │
          ▼
     объединение кандидатов
          │
          ▼
       Top-50
```

При этом важно понимать:

> Любой метод, который уменьшает Recall на этапе candidate generation, потенциально необратимо теряет релевантные объявления.

Поэтому при сравнении методов необходимо в первую очередь измерять их влияние на Recall@50.

Reranker имеет смысл только в том случае, если его использование помогает сформировать более полный набор кандидатов. Если уже сформирован набор из 50 кандидатов и метрика зависит только от принадлежности к этому набору, дополнительное ранжирование этих 50 объектов само по себе Recall@50 не увеличивает.

Для повышения Recall разумно исследовать **объединение кандидатов из нескольких независимых retrieval-методов**, например:

```text
BM25 candidates
        +
Dense retrieval candidates
        +
Exact / fuzzy matching
        +
Category/location matching
        +
другие правила
        ↓
объединённый candidate pool
        ↓
выбор 50 кандидатов
```

Главный экспериментальный вопрос:

> Какие признаки и retrieval-стратегии позволяют увеличить вероятность попадания каждого релевантного объявления в candidate pool размером 50?

Все решения необходимо проверять на локальной валидации, построенной только из `train.parquet`, не используя benchmark-разметку.
